Agents that coordinate through the trail they share.

stiggy runs fleets of AI agents on NATS. Every decision, handoff and human answer is written to a durable event log, so a fleet survives crashes, scales out across machines, and can be replayed, forked and rewound.

go install github.com/henomis/stiggy/cmd/stiggy@latest

Named after stigmergy

Ants don't hold meetings. Each one leaves a trace in the ground, and the next one reads it. The colony's plan lives in the environment, not in any single ant.

stiggy works the same way. Agents never call each other through fragile in-memory state: a step finishes, its output and its routing choice land in the execution's event log on JetStream, and the next step picks them up from there. Kill a worker halfway through and another one carries on from the last trace.

Describe the fleet once

Write it as YAML and run it with the stiggy binary, or build it in Go. Both produce the same model, checked before anything runs.

namespace: newsroom
models:
  fast: {provider: ollama, model: llama3.2-eco}
agents:
  researcher: {model: fast, role: Researcher, goal: "Find accurate, recent facts."}
  writer: {model: fast, role: Writer, goal: "Write short, clear articles."}
crews:
  article:
    tasks:
      - {id: research, agent: researcher, description: "Research {{.input.topic}}."}
      - {id: write, agent: writer, description: Write a 200-word article from the research.}
app, _ := stiggy.New(nc,
    stiggy.WithNamespace("newsroom"),
    stiggy.WithModel("fast", openai.New("ollama",
        openai.WithBaseURL(openai.OllamaBaseURL), openai.WithModel("llama3.2-eco"))),
    stiggy.WithAgent("researcher", spec.Agent{Model: "fast", Role: "Researcher"}),
    stiggy.WithAgent("writer", spec.Agent{Model: "fast", Role: "Writer"}),
    stiggy.WithCrew("article", spec.Crew{Tasks: []spec.Task{
        {ID: "research", Agent: "researcher", Description: "Research {{.input.topic}}."},
        {ID: "write", Agent: "writer", Description: "Write a 200-word article from the research."},
    }}),
)

go app.Run(ctx)
<-app.Ready()

id, _ := app.Client().Start(ctx, "article", map[string]any{"topic": "NATS"})
st, _ := app.Client().Wait(ctx, id)
$ nats-server -js &
$ stiggy validate fleet.yaml      # every problem, with its line
$ stiggy compile fleet.yaml       # the flows it becomes
$ stiggy run fleet.yaml &         # serve it
$ stiggy start -ns newsroom article -input '{"topic": "NATS"}' -wait
  • Strict by default. Unknown keys are errors. stiggy validate reports every problem at once, each with its file line.
  • Any model. OpenAI, Anthropic, Ollama or any OpenAI-compatible endpoint, with retries and per-process rate limits.
  • Real tools. Shell, files, skills, key-value storage, MCP servers, retrieval over Qdrant, Postgres or Weaviate.

Six team shapes, ready to use

Each shape is a few lines of YAML that expand into an ordinary durable flow. Run stiggy compile to see exactly what it becomes.

  • Crew

    Tasks in order, with parallel async tasks, a guardrail agent that sends work back, or a manager that assigns it.

  • Supervisor

    One agent routes to a worker at a time and gets the report back, until it answers without routing.

  • Swarm

    Every agent may hand off to any other. The first agent that answers without handing off ends it.

  • Evaluator and optimizer

    A writer drafts, an evaluator passes it or returns feedback, for up to a set number of rounds.

  • Debate

    Debaters argue in parallel for several rounds, each seeing the transcript so far. A judge decides.

  • Plan and execute

    A planner lists steps, an executor runs them in parallel, an optional synthesizer combines the results.

Need something else? Write the flow yourself: choices, fan-out and join, maps, subflows, waits, retries and budgets are all there, with agents as steps.

Go back to any point and try again

An execution is its event log. Read the state right after any event, branch a new execution from it with different input, or rerun from one step after fixing a prompt. Routing choices and human answers are in the log too, so a fork sees exactly its own history.

Select an event to see the command.

stiggy get <exec> -seq 12

The state as it was right after event 12.

One file on every machine

Each process runs the same fleet file and picks its part. Add worker processes when the queue grows; stop one and its jobs are redelivered.

stiggy run -role engine  -http :8080 fleet.yaml                # drives executions, timers, schedules
stiggy run -role workers -http :8080 fleet.yaml                # runs agents; scale it out
stiggy run -role workers -only researcher,writer fleet.yaml    # dedicated hosts for some agents
  • Cap the cost. Budgets cap agent steps, input and output tokens and dollars per execution, charged even for failed runs.
  • Keep people in the loop. An agent can ask a human a question, or have every answer reviewed, and the execution waits durably for the reply.
  • Talk to other teams. Expose agents and flows on the NATS Agent Protocol, and use other teams' agents as steps or delegates.

Or draw it

stiggy design opens a canvas in your browser. Connect blocks for agents, routers, loops, conditions, parallel branches, human approval and agent teams, and every save writes a fleet file checked by the same compiler as stiggy validate.
